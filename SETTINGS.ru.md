# Настройки luci-app-trusttunnel — полный справочник

Каждый параметр описан так: что делает, что бывает если тронуть, и когда это
вообще нужно. Значение по умолчанию указано в скобках у заголовка.

Все настройки живут в `/etc/config/trusttunnel` и правятся либо через интерфейс
(**Службы → TrustTunnel**), либо через `uci`. После правки через `uci`
обязателен `uci commit trusttunnel` и перезапуск службы — сама она изменения не
подхватывает.

Файл `/etc/config/trusttunnel` объявлен в `conffiles` пакета, поэтому
обновление пакета его не затирает.

---

## Как это работает — коротко, но по существу

Понимание одного механизма избавляет от большинства вопросов ниже.

Трафик отбирается **не** маршрутом по умолчанию, а по цепочке из трёх звеньев:

1. **dnsmasq** получает директивы `nftset=` на каждый домен из выбранных
   списков. Когда клиент в сети спрашивает такой домен, dnsmasq кладёт
   полученные адреса в множество nftables `tt_bypass4`/`tt_bypass6`.
2. **nftables** помечает отметкой `fwmark` пакеты, идущие к адресам из этого
   множества.
3. **Правило маршрутизации** отправляет помеченные пакеты в отдельную таблицу
   (по умолчанию 880), где маршрут по умолчанию ведёт в туннель.

Отсюда два важных следствия. Первое: без `dnsmasq-full` режим «обход по
списку» не работает вовсе, потому что штатный dnsmasq не понимает `nftset=`.
Второе: домен попадает в обход только после того, как его **кто-то запросил** —
множество наполняется по факту резолвинга, а не заранее.

**Устройство туннеля создаёт клиент TrustTunnel, а не этот пакет.** Мы лишь
привязываем к нему маршрут после того, как оно появилось. Имя выбирает клиент
(обычно `tun0`), задать его нельзя — в схеме конфигурации клиента такого
параметра нет. Фактическое имя показано на странице состояния.

## Секция `main` — общее

### `enabled` (`0`)

Запускать ли службу при загрузке роутера. В интерфейсе — флажок
**«Включить»**.

Это не то же самое, что кнопка «Запустить»: кнопка поднимает службу сейчас,
а этот флаг определяет поведение после перезагрузки. Если флаг выключен, при
старте системы служба сообщает в журнал «disabled in configuration, not
starting» и ничего не делает.

Тонкость, на которой стоит остановиться, потому что на её смешении однажды
держался дефект. За автозапуск в OpenWrt отвечают **два** независимых
механизма: ссылка init-скрипта в `/etc/rc.d/` — её создаёт установка пакета,
всегда, — и этот флаг, который проверяется уже внутри запуска. Первый решает,
будет ли служба вообще вызвана при загрузке; второй — сделает ли она что-нибудь.
Если ссылки нет, флаг не имеет значения: туннель не поднимется после
перезагрузки, и в журнале не будет ни одной строки. Проверить наличие можно
так:

```sh
ls /etc/rc.d/ | grep trusttunnel
```

Должны быть `S95trusttunnel` и `K10trusttunnel`.

### `mode` (`selective`)

Принцип отбора трафика. Два значения:

- **`selective`** — «обход по списку». В туннель уходят только адреса доменов
  из выбранных списков. Всё остальное идёт напрямую. Требует `dnsmasq-full`.
- **`full`** — «всё через VPN». В туннель уходит весь трафик, пересылаемый из
  локальной сети, а исключения обрабатывает сам клиент по имени сервера в
  TLS-рукопожатии. Списки в этом режиме не используются, `dnsmasq-full` не
  требуется.

Смена режима меняет и генерируемый конфиг dnsmasq, и набор правил nftables,
поэтому требует перезапуска службы. Интерфейс делает это сам при «Сохранить и
применить».

### `full_exclude_lists` (`0`)

Только для режима `full`. Отдаёт домены из выбранных списков клиенту как
список исключений — то есть они пойдут напрямую, минуя туннель.

Обратная логика по сравнению с селективным режимом: там списки определяют, что
**идёт** в туннель, здесь — что **не идёт**.

Осторожно с объёмом: несколько тысяч записей заметно увеличивают потребление
памяти клиентом. Списки на десятки тысяч доменов сюда лучше не отдавать.

### `log_level` (`info`)

Подробность журнала клиента: `info`, `debug`, `trace`.

`debug` и особенно `trace` пишут очень много и на роутере с медленной флешкой
могут заметно нагрузить систему. Включайте на время разбирательства и
возвращайте `info`.

## Секция `endpoint` — сервер

Быстрый способ заполнить всю секцию — **«Импорт конфига сервера»** на странице
настроек. Принимаются оба вида, которые выдаёт сервер: текст файла конфигурации
и ссылка `tt://`. Они различаются автоматически.

### `hostname` (пусто)

Имя хоста для TLS-рукопожатия. **Не** используется для маршрутизации — только
для проверки сертификата и SNI.

Без него TLS-сессия устанавливается на сам адрес, и многие серверы такое
отвергают. Если сервер отказывает в соединении, а адрес заведомо верный —
проверьте это поле первым.

### `username`, `password` (пусто)

Доступы к серверу. Пароль хранится в `/etc/config/trusttunnel` в открытом виде
— как и все пароли в UCI. Файл доступен только root.

Пароль попадает в генерируемый `/var/etc/trusttunnel/client.toml`, который
создаётся с правами `600` в каталоге с правами `700`.

### `address` (список, пусто)

Адреса сервера в виде `хост:порт` или `[ipv6]:порт`. Можно указать несколько —
клиент сам выберет отвечающий, по результатам своих измерений задержки.

Это единственный обязательный параметр: без адреса генерация конфигурации
отказывает и служба не запускается — в журнале будет «configuration generation
failed».

### `protocol` (`http2`)

Транспорт для соединения с сервером. Значение должен подсказать владелец
сервера; наугад менять смысла нет.

### `anti_dpi` (`0`)

Дополнительные меры против анализа трафика провайдером. Включайте, если
соединение устанавливается, но быстро обрывается или работает нестабильно —
это типичный признак вмешательства DPI.

Не бесплатно по накладным расходам, поэтому по умолчанию выключено.

### `post_quantum` (`1`)

Постквантовая группа при согласовании ключей. Включено по умолчанию; выключать
стоит только если сервер её не поддерживает и соединение из-за этого не
устанавливается.

### `skip_verification` (`0`)

Отключает проверку сертификата сервера.

**Это снимает защиту от подмены сервера.** Единственный оправданный случай —
отладка с самоподписанным сертификатом, и даже тогда правильнее закрепить
сертификат через `certificate`, а не отключать проверку целиком.

### `certificate` (пусто)

PEM-сертификат сервера для закрепления. Если задан, хранилище доверия системы
не используется и `ca-bundle` не требуется.

Записывается в `/var/etc/trusttunnel/endpoint.pem` с правами `600`.

### `dns_upstream` (список, пусто)

DNS-резолверы, которыми пользуется **сам клиент** для своих нужд — например
для доменов-исключений, которые он разрешает заранее.

Это **не** резолвер для доменов из списков: те резолвит роутер, см. `list_dns`
в секции `network`. Проверено опытом: если подставить в `list_dns` заведомо
мёртвый адрес, резолвинг обходных доменов истекает по таймауту — значит запросы
идут туда, а не через клиента.

Принимаются форматы, которые документирует сам клиент: обычный адрес
`1.1.1.1:53`, `tcp://`, `tls://` для DoT, `https://` для DoH, `quic://` для
DoQ и `sdns://` для DNS-стампов. Пусто означает значение по умолчанию у
клиента — AdGuard DNS без фильтрации.

### `has_ipv6` (`1`)

Сообщает клиенту, что сервер доступен по IPv6.

## Секция `network` — маршрутизация

Эти параметры почти никогда не нужно менять. Исключение — `mtu` и
`lan_devices`.

### `mtu` (`1350`)

MTU туннельного устройства. Значение передаётся клиенту, который применяет его
к своему устройству — сами мы устройство не настраиваем.

Зачем это важно: зона фаервола создаётся с `mtu_fix='1'`, и зажим MSS берёт
величину из MTU устройства. Если значение окажется больше реального, симптом
будет характерный и обманчивый — **мелкие страницы открываются, а TLS-рукопожатия
и большие загрузки подвисают**. Ни один индикатор этого не покажет, потому что
на уровне маршрутизации всё исправно.

Уменьшайте, если наблюдаете именно такую картину.

### `table` (`880`)

Номер таблицы маршрутизации для помеченного трафика.

Менять нужно только при конфликте с другим пакетом, который занял тот же
номер. Допустимый диапазон — 1…252.

### `fwmark` (`0x9527`)

Отметка, которую nftables ставит на отбираемые пакеты и по которой правило
маршрутизации отправляет их в отдельную таблицу.

Менять — только при конфликте с mwan3, SQM или другим пакетом, работающим с
отметками. Принимается десятичное или шестнадцатеричное значение в пределах
32 бит.

### `blackhole_on_down` (`1`)

Killswitch. Пока туннель не поднят, помеченный трафик упирается в
blackhole-маршрут и отбрасывается, а не утекает напрямую.

Выключать стоит осознанно: без него в момент обрыва туннеля трафик, который вы
намеренно направили в туннель, пойдёт открыто.

Механика: blackhole ставится с метрикой 1000, а маршрут в туннель — с метрикой
1, поэтому он перекрывает blackhole как только появляется устройство.

### `include_router_traffic` (`0`)

Направлять в туннель не только пересылаемый трафик из сети, но и трафик самого
роутера.

По умолчанию выключено, и это осознанно: собственные запросы роутера — это, в
частности, обновление списков, проверка обновлений и разрешение имени самого
сервера. Их уход в туннель создаёт зависимость от туннеля у того, что должно
работать до его подъёма.

### `intercept_dns` (`0`)

Перехватывать DNS-запросы клиентов сети, направленные на сторонние серверы, и
разворачивать их на dnsmasq роутера. Дополнительно отклоняет DNS-over-TLS
(порт 853).

Зачем: в селективном режиме отбор держится на ответах **роутерного** dnsmasq.
Клиент, который спрашивает 8.8.8.8 напрямую или использует DoH, обходит этот
механизм — и его трафик к домену из списка в туннель не попадёт.

Осмысленно только в селективном режиме; в режиме `full` не применяется.

### `list_dns` (`plain`)

Кто резолвит домены из списков и чем защищён запрос. Три значения, и разница
между ними существенная.

**`plain`** — обычный DNS на адрес из `list_resolver`. Адрес резолвера
помещается в набор обхода, поэтому запрос уходит **внутрь туннеля**: провайдер
его не видит и не может подменить ответ. Если бы мог, в набор попали бы
подставные адреса и обход перестал бы работать.

**`doh`** — шифрованный DNS. Служба поднимает на роутере локальный
`https-dns-proxy` и направляет dnsmasq на него. Запрос уходит шифрованным, но
**напрямую, а не через туннель**: провайдер видит обращение к резолверу, но не
содержимое. В набор обхода адрес не добавляется — шифрованному запросу туннель
не нужен.

Это единственный способ получить фильтрацию по своему профилю, например
NextDNS. Пакет `https-dns-proxy` в зависимостях не объявлен: если его нет,
строки `server=` не выдаются вовсе — домены резолвит провайдер, обход
продолжает работать, а диагностика говорит, что поставить.

После `apk add https-dns-proxy` обязательно выключите его собственный
init-сервис: при установке он стартует сам и переписывает DNS всей сети на
себя, направляя dnsmasq на резолвер Google по умолчанию, который у многих
провайдеров не отвечает. Нам нужен только бинарник — свой экземпляр служба
поднимает сама. Точные команды и объяснение — в README, раздел про DNS.
Диагностика замечает включённый пакетный сервис и предупреждает.

**`provider`** — своего резолвера не задаём, домены резолвит то, что уже
настроено на роутере.

Почему в режиме `plain` нельзя указать DoT или DoH напрямую: значение уходит в
директиву dnsmasq `server=`, а она принимает только обычный адрес. Именно
поэтому шифрование сделано отдельным режимом с прокси, а не настройкой поля.

### `list_resolver` (`1.1.1.1`)

Адрес резолвера для режима `plain`. Принимается запись `адрес#порт` — она
нужна, если вы поднимаете свой DoT-прокси вручную: `stubby` слушает
`127.0.0.1#5453`, `https-dns-proxy` — `127.0.0.1#5053`.

### `list_doh_url` (пусто)

Адрес DoH-резолвера для режима `doh`. Только `https://`. Для NextDNS со своим
профилем: `https://dns.nextdns.io/<ваш-id>`.

### `list_doh_port` (`5460`)

Локальный порт, на котором слушает поднимаемый нами `https-dns-proxy`. Менять
только при конфликте: `5053` занимает пакетный init того же прокси, `5453` —
`stubby`.

При включённом `doh_network` не используется: своего экземпляра в том режиме нет
вовсе, работает штатный `https-dns-proxy` на своих портах.

### `doh_network` (`0`)

Делает резолвер из `list_doh_url` DNS **всей сети**, а не только доменов из
списков.

Без него настройка работает не так, как читается. Резолвер обслуживает ровно
те домены, для которых генератор выдал `server=/домен/127.0.0.1#5460`, — то
есть списочные. Всё остальное резолвит то, что настроено на роутере: обычно
штатный `https-dns-proxy` со своими Cloudflare и Google. Любая проверялка
(`test.nextdns.io`, dnsleaktest) в списках не лежит и показывает чужой
резолвер — отсюда стойкое впечатление, что настройка не сработала.

Как это сделано. Пока служба работает, она прописывает ваш URL в `resolver_url`
**всех** экземпляров штатного `https-dns-proxy` и перезапускает его; при
остановке возвращает сохранённые значения. Конфиг dnsmasq мы не трогаем:
`noresolv` и `server=127.0.0.1#5053` пишет init того пакета, у которого для
этого есть свой механизм с бэкапом.

Почему нельзя проще — своим снипетом в conf-dir. Проверено на живом роутере
отдельным экземпляром dnsmasq: wildcard-домен `/#/` приоритета над
бездоменными `server=` не имеет и попадает с ними в один пул. При
`server=127.0.0.1#5053` рядом с `server=/#/127.0.0.1#5460` отвечал Cloudflare.
Резолвер обслуживал бы «иногда» — хуже честного «никогда».

Цена режима, о которой стоит знать заранее:

- при старте и остановке службы перезапускается dnsmasq, и сеть на долю
  секунды остаётся без DNS;
- если резолвер перестанет отвечать, без DNS останется вся сеть: у dnsmasq
  стоит `noresolv`, других upstream нет. Диагностика спрашивает каждый
  прописанный экземпляр и жалуется на молчащий;
- строки `server=` для доменов из списков в этом режиме не выдаются — они
  указывали бы на тот же резолвер, что и общий upstream. Обход при этом жив:
  его держат строки `nftset=`;
- если правили `resolver_url` руками, пока флаг стоял, служба заметит это при
  остановке и не станет затирать правку своим бэкапом — но и прежние значения
  тогда не восстановит;
- по умолчанию выключен, обновление пакета его не включает.

Работает только вместе с `list_dns=doh` и только в режиме `selective`.

### `lan_devices` (пусто)

Список локальных интерфейсов, трафик с которых отбирается. Пусто означает
«взять `network.lan.device` из настроек системы», что почти всегда правильно.

Заполняйте, если у вас несколько локальных сетей и туннель нужен не для всех:
например `br-lan br-guest`.

## Секция `lists` — списки доменов

### `auto_update` (`1`)

Обновлять выбранные списки по расписанию. Задание cron ставится при установке
пакета на 04:17 — время смещено от круглого часа намеренно, чтобы не обращаться
к GitHub одновременно со всеми.

Если выключить, задание остаётся, но обновление не выполняется: проверка флага
происходит внутри.

### `update_interval` (`daily`)

Периодичность обновления.

### `source` (список, пусто)

Выбранные файлы списков доменов из репозитория `itdoginfo/allow-domains`,
например `Services/youtube.lst`. В интерфейсе выбираются флажками на странице
**«Списки»**.

Каталог доступных списков подтягивается с GitHub и кэшируется на сутки.

### `subnet` (список, пусто)

Файлы со списками подсетей. Их содержимое попадает в множество обхода напрямую,
без участия DNS, — то есть работает даже для соединений по IP-адресу.

### `url` (список, пусто)

Ссылки на свои списки. Принимаются только `http://` и `https://`, размер
ограничен 10 МБ.

Имейте в виду: файл сохраняется по имени из ссылки, поэтому два разных адреса с
одинаковым последним элементом перезапишут друг друга.

## Секция `domains` — свои домены

### `bypass` (список, пусто)

Домены, которые нужно направить в туннель дополнительно к спискам. Удобно для
единичных сайтов, ради которых нет смысла подключать целый список.

### `direct` (список, пусто)

Домены, которые нужно исключить из обхода, даже если они есть в выбранных
списках. Имеет приоритет над `bypass` и над списками.

На странице состояния число снятых записей показано отдельной строкой — иначе
было бы непонятно, почему выбранный домен не попал в обход.

## Что смотреть, когда не работает

Первым делом — кнопка **«Проверить»** на странице состояния. Она прогоняет всю
цепочку и пишет не только вердикт, но и что делать с найденным.

Разница между двумя строками в её выводе стоит того, чтобы её понимать:

- **«Устройство туннеля»** — создал ли клиент своё устройство. Если нет, дело в
  клиенте, и смотреть надо его журнал.
- **«Маршрут привязан к устройству»** — направлен ли помеченный трафик в это
  устройство. Устройство может существовать, а маршрута не быть, и тогда трафик
  уходит в killswitch. Именно этот разрыв когда-то делал селективный режим
  неработающим при внешне исправном состоянии.
- **«Носитель туннеля»** — установил ли клиент соединение с сервером. Носитель
  появляется только после успешного подключения.
